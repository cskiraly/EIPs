## Abstract

[EIP-7732](./eip-7732.md) propagates the execution payload as a single message on the `execution_payload` gossipsub topic. This EIP replaces that topic with `execution_payload_chunks`, which carries the payload envelope split into `TOTAL_EXECUTION_PAYLOAD_CHUNKS` chunks. The builder commits to the chunk set with a Merkle root carried in the execution bid, so each chunk is independently verifiable from a single block signature check plus an inclusion proof.

## Motivation

The gas-limit growth that [EIP-7732](./eip-7732.md) enables implies larger payloads leading to increased latency. If Payload Timeliness Committee (PTC) members do not receive the payload within the attestation deadline, an otherwise valid payload is considered missed.

The existing `execution_payload` gossipsub topic scales poorly as payloads grow. Two effects dominate:

1. Once a peer has received a large message, it is hard to cancel in-flight duplicates, so the same bytes arrive several times and consume bandwidth that could carry new data.
2. A peer must download the full message before it can forward any of it, so each hop adds a full transfer, leading to increased latency proportional to message size multiplied by hop count.

Both effects are mitigated when the message is chunked. Large duplicates are impossible with chunk granularity, and a peer can forward each chunk as soon as it arrives, so hops overlap instead of serializing.

### Commitment

The execution bid commits to the chunked envelope:

```python
class ExecutionPayloadBid(ProgressiveContainer):
    ...
    payload_chunks_root: Root  # [New in this EIP]
    ...
```

`payload_chunks_root` is the SSZ `hash_tree_root` of the `Vector[Bytes32, TOTAL_EXECUTION_PAYLOAD_CHUNKS]` of SHA-256 hashes of the chunks of the serialized `ExecutionPayloadEnvelope`, as computed by `compute_payload_chunks_root` in the Chunking section. A receiver therefore verifies one block signature and, per chunk, one Merkle inclusion proof. Once the envelope is reconstructed, it MUST pass the checks that gossip validation of a `SignedExecutionPayloadEnvelope` makes today against the block and its bid: the slot, the builder index, the block hash, the execution requests root, and the request and withdrawal limits. The two checks that take the signature and `beacon_block_root` have no object under this EIP; see Security Considerations.

### Envelope

Chunking is applied to the envelope:

```python
class ExecutionPayloadEnvelope(ProgressiveContainer):
    ACTIVE_FIELDS = Bitvector[5](1, 1, 1, 0, 1)  # [Modified in this EIP] `beacon_block_root` inactive

    payload: ExecutionPayload
    execution_requests: ExecutionRequests
    builder_index: BuilderIndex
    # [Modified in this EIP] removed `beacon_block_root`
    parent_beacon_block_root: Root
```

The fields, their order and the container kind are those of the Gloas `ExecutionPayloadEnvelope`, with `beacon_block_root` removed; its position is left inactive. The serialized bytes are what the commitment covers, so this listing has to be exact. `beacon_block_root` is removed because it is not known at the time of envelope construction.

Under [EIP-7732](./eip-7732.md) the builder constructs the envelope after observing that its bid was included, and can therefore embed the beacon block root. Under this EIP the builder must commit to the chunks when it produces the bid — before the block exists — so the root cannot be part of the committed bytes. It is instead carried per chunk in the `PayloadChunk` message, together with the `payload_chunks_root` committed in the bid:

```python
class PayloadChunk(Container):
    payload_chunks_root: Root
    index: ChunkIndex
    chunk: Chunk
    chunk_inclusion_proof: Vector[Bytes32, CHUNK_INCLUSION_PROOF_DEPTH]
    slot: Slot
    beacon_block_root: Root
```

`payload_chunks_root` matches the commitment in the bid and identifies the chunk set. A receiver verifies the inclusion proof against it as soon as the chunk arrives, and forwards the chunk once a valid beacon block for the slot has named this root in its bid.

`slot` and `beacon_block_root` sit outside the inclusion proof and are unauthenticated hints: `slot` allows windowing a chunk cheaply and MUST equal the slot of a bid committing to `payload_chunks_root`, while `beacon_block_root` lets a receiver locate or request the corresponding beacon block and MUST equal the root of the block containing that bid. Receivers MUST NOT treat either field as authenticated and MUST use them only as hints: to window a chunk and to route lookups; a chunk is bound to a bid solely through `payload_chunks_root`.

### Chunking

The builder MUST derive the chunks, and therefore `payload_chunks_root`, as follows. No padding is added: the last non-empty chunk can be shorter, and trailing chunks can be empty.

```python
def compute_payload_chunks(
    envelope: ExecutionPayloadEnvelope,
) -> Vector[Chunk, TOTAL_EXECUTION_PAYLOAD_CHUNKS]:
    data = ssz_serialize(envelope)
    chunk_size = (len(data) + TOTAL_EXECUTION_PAYLOAD_CHUNKS - 1) // TOTAL_EXECUTION_PAYLOAD_CHUNKS
    chunks = []
    for i in range(TOTAL_EXECUTION_PAYLOAD_CHUNKS):
        start = i * chunk_size
        chunks.append(Chunk(data[start:start + chunk_size]))
    return chunks


def compute_payload_chunks_root(envelope: ExecutionPayloadEnvelope) -> Root:
    leaves = Vector[Bytes32, TOTAL_EXECUTION_PAYLOAD_CHUNKS](
        [hash(chunk) for chunk in compute_payload_chunks(envelope)]
    )
    return hash_tree_root(leaves)
```

Each leaf is `hash(chunk)`, the SHA-256 hash of the chunk's bytes; `chunk_inclusion_proof` is the corresponding Merkle branch:

```python
def verify_payload_chunk_inclusion_proof(payload_chunk: PayloadChunk) -> bool:
    return is_valid_merkle_branch(
        leaf=hash(payload_chunk.chunk),
        branch=payload_chunk.chunk_inclusion_proof,
        depth=CHUNK_INCLUSION_PROOF_DEPTH,
        index=payload_chunk.index,
        root=payload_chunk.payload_chunks_root,
    )
```

Receivers concatenate chunks `0` through `TOTAL_EXECUTION_PAYLOAD_CHUNKS - 1` and deserialize the result; nothing is stripped, since each leaf hashes its chunk's exact bytes.

### Networking

This EIP introduces the `execution_payload_chunks` gossip topic and removes `execution_payload`. The topic carries `PayloadChunk` messages.

Once the builder has successfully processed a beacon block containing its bid, it SHOULD construct the `TOTAL_EXECUTION_PAYLOAD_CHUNKS` `PayloadChunk` messages and publish them to the topic; it SHOULD NOT publish them until it has successfully processed that block. As under Gloas's rule for an honestly withheld payload, it MAY withhold them when the block was not timely and is therefore not the head of its chain.

Messages on the topic use the `message-id` of the Altair networking specification, the hash of the topic and the uncompressed message. A chunk that passes validation has one byte form per block: `payload_chunks_root`, `index`, `chunk` and `chunk_inclusion_proof` are fixed by the commitment, and `slot` and `beacon_block_root` by the block that validation checks them against. Every node's copy of a chunk is therefore the same gossipsub message, and duplicate suppression, `IHAVE` and `IWANT`, and `IDONTWANT` name a chunk by that id with no rule of this EIP. The id is not derived from the commitment; the Rationale says why.

#### Seen cache

The `Seen` cache used by the gossip validation functions is extended to track received chunks:

```python
@dataclass
class Seen:
    ...
    payload_chunk_tuples: set[tuple[Root, ChunkIndex]]  # [New in this EIP]
```

`payload_chunk_tuples` records the `(payload_chunks_root, index)` pair of every accepted chunk, analogous to `data_column_sidecar_tuples` for column sidecars, and backs the first-seen check below.

#### Gossip validation

The following validations MUST pass before a node forwards a `PayloadChunk` `chunk` on the topic.

- _[IGNORE]_ `chunk.slot` equals the current slot, within `MAXIMUM_GOSSIP_CLOCK_DISPARITY` allowance.
- _[REJECT]_ `chunk.index` is less than `TOTAL_EXECUTION_PAYLOAD_CHUNKS`.
- _[REJECT]_ The inclusion proof is valid as verified by `verify_payload_chunk_inclusion_proof(chunk)`.
- _[IGNORE]_ The node has seen a valid beacon block for `chunk.slot` whose bid commits to `chunk.payload_chunks_root`. A chunk that fails only this check MUST be buffered as described below and revalidated when such a block is seen.
- _[IGNORE]_ `chunk.beacon_block_root` is the root of such a block.
- _[IGNORE]_ `(chunk.payload_chunks_root, chunk.index)` is not present in `seen.payload_chunk_tuples` (first-seen per commitment and index); the tuple is added upon acceptance.

A beacon block is seen once it has passed gossip validation on the `beacon_block` topic, or once it has been processed, as a block fetched by root is; gossip validation alone is enough. Validation and forwarding of a chunk MUST NOT wait for the other chunks of its set: a chunk that passes these validations is forwarded on its own, whether pushed or announced, and kept until the envelope can be reconstructed.

#### Buffering before the block

A chunk whose block is not yet seen MUST be held in a buffer bounded in two ways: at most `TOTAL_EXECUTION_PAYLOAD_CHUNKS` chunks per `payload_chunks_root`, and a per-peer reservation, so that no peer can exclude another peer's copy of the same chunk. Only chunks that have passed the slot, index and inclusion proof checks above enter the buffer. Buffered chunks are revalidated when a valid beacon block for their slot is seen, and dropped at the end of their slot (within `MAXIMUM_GOSSIP_CLOCK_DISPARITY`).

## Rationale

**Why a Merkle commitment.** Alternatives such as KZG place proof generation on the builder's critical path. A Merkle tree over chunks is cheap enough to build at bid time, and a single root in the bid makes each chunk self-verifying against one already-verified signature.

**Why the root travels in the chunk.** `payload_chunks_root` in the message carries no authority of its own. It lets a receiver verify the inclusion proof the moment the chunk arrives, and key its buffer and the first-seen check by the set the chunk claims to belong to, before the block that names that set has arrived. A chunk whose proof fails against the root it carries is rejected at the first hop; a root no block has named authenticates nothing. `slot` and `beacon_block_root` are hints for the same reason: they help a receiver find the block, and the consistency checks in gossip validation are all that holds them to it.

**Why the message id is the content id.** An id computed from `payload_chunks_root` and `index` alone was considered. A node could then compute the id of every chunk of a set from the bid, request exactly the chunks it lacks when they are announced, decline announced ids under roots it cannot authenticate, and tell its peers which chunks it holds. It was rejected because of how gossipsub implementations treat ids. For example, go-libp2p-pubsub records an id as seen before the application's validator runs and keeps it seen whatever the validator decides; later copies received from peers are dropped as duplicates and are not requested when announced. With an id anyone can compute from public data, and the root and the index are public once the block is, a peer could send a garbage message under the honest chunk's id ahead of the chunk itself and have the honest chunk refused as a duplicate at every node its garbage reached first, for the rest of the slot. The content id has no such weakness: a message that differs from the honest chunk in any byte has another id, so no peer can occupy the honest chunk's id. And since every byte of a valid chunk is fixed by the commitment and the block, the content id names the chunk as well as a computed one would for every node that holds it. What the computed id would have added, requests by index for chunks a node has never seen announced, needs an announcement protocol that decides for itself when an id counts as seen, and is outside this EIP.

**Why a chunk waits for its block.** A chunk is forwarded only once a valid beacon block for its slot has named its root. The block is the one object that says which bid was chosen. Gossip validation accepts only the first block per proposer and slot, but additional processed blocks can open the gate for additional chunk sets at the same node; producing those blocks is slashable equivocation (see Security Considerations and the open questions). Processing the block then checks that the bid is signed and funded, or is a self-build of zero value; whether the builder pays follows Gloas's settlement rules. The wait costs less than it appears. The gate needs only the bid's root, which is in the body of any signature-valid block, so it opens on gossip validation of the block, not on processing it. Along a path the wait is usually paid once, at the first node the chunks reach before the block; a downstream node has usually had the block for as long as its upstream did, less one link, so it does not wait again. Blocks and chunks travel on different topics and meshes, so a node can still receive a chunk first and wait. In simulation the holds sat at a handful of nodes near the source, and every node met the slot's deadline.

Four alternatives were considered.

_Forwarding against any accepted bid._ An earlier revision of this EIP forwarded a chunk as soon as a bid accepted on the bid topic had committed to its root, so that no node would wait for the block. Bid gossip accepts one bid per builder and parent per slot, and a bid that is not chosen costs its builder nothing, so every accepted bid could put a full chunk set on the network for free. It also let a payload travel ahead of its block: a builder that also controls the proposer could release the payload while holding the block back. Reviewers of that revision asked how a node would know that a gossiped bid was the chosen one; it cannot, and the block is what says so.

_Waiting for the block to be processed._ Gating on a processed block, as the `execution_payload` topic does today, makes the anchor exactly as strong as the receiver's own state transition, but adds its latency to the wait at the first node, and the root does not need it: it is read from the block body once the proposer's signature is valid. The equivocation this admits is discussed under Security Considerations. A block that passes gossip validation but fails processing, over a forged bid or for any other reason, still opens the gate for its set, so nodes can forward chunks for a block they then discard; today they forward no envelope for such a block. If it is the proposer's only block for the slot, the proposer loses the slot; a second block would be a slashable equivocation. The chunks of such a block can come from its builder, if the builder publishes before processing the block (see Networking), or from anyone who holds them, forwarded under that block's hints.

_Checking the bid's signature at the gate._ Each node could also verify the builder's signature on the bid, once per block, reusing the check if the bid already passed the bid topic; a self-build has no such signature and would stay exempt. That keeps forged bids out, but not a block that fails processing for another reason, such as an unfunded bid, a wrong state root or an invalid attestation. For a bid from an external builder whose signature is not already verified, it can delay forwarding where chunks arrive before their block; it does not prevent a proposer from equivocating to authorize additional sets, including at a node that processes the additional blocks.

_A fast lane for roots seen on the bid topic._ Chunks whose root belongs to a bid accepted on the bid topic could be exempt from the per-peer reservation of the buffer, since their set is already bounded by bid validation. This was rejected because it favours builders that bid through the topic over a proposer that builds its own payload, whose root never appears there: the two would meet different buffer rules at the same node for the same kind of message.

Chunks that arrive before their block are buffered rather than dropped. The objection that a buffer of unauthenticated data is a denial-of-service surface is met by bounds rather than by refusal: the inclusion proof is checked against the carried root before a chunk enters, the buffer holds at most one set per root, and a per-peer reservation keeps one peer from excluding another peer's copy. Dropping instead would cost the self-building proposer most, since its block and its chunks travel on different topics and the chunks overtake the block at the nodes nearest the source; and go-libp2p-pubsub records a message as seen before the application's validator runs, so a dropped chunk is refused as a duplicate from every other peer and is not requested when announced, until the seen cache forgets it, which takes longer than the slot.

**The envelope's signature.** This EIP chunks the envelope, not the `SignedExecutionPayloadEnvelope`, and so far says nothing about the signature. There are two ways to settle it. The first drops it: a payload counts as revealed once it is reassembled from chunks that verify under the root the block's bid commits to, and fork choice, the payload timeliness committee and recovery by root are respecified to take that object. This changes what a reveal is. The builder loses exclusive control over revealing, since anyone holding the bytes can complete the reveal, a reveal can no longer be made for one block and withheld from another carrying the same bid, and a partial release has made most of the transactions public without revealing anything. The second keeps it: the builder signs the ordinary Gloas envelope, whose block root it knows once the block exists, and broadcasts the signature on its own, as a small message carrying the block root and what a receiver needs to verify it. A receiver that has reassembled the chunks and holds the block then holds an ordinary signed envelope, and nothing downstream of gossip changes. It costs one more message per payload, and the payload is not revealed until that message arrives. The second keeps the consensus layer as it is, which is the reason to prefer it unless the first's change is wanted for its own sake; the choice is open.

**Why a wrong `beacon_block_root` is ignored, not rejected.** The field is a lookup hint outside the proof, and a mismatch has honest causes: a proposer who signs two blocks with the same bid makes chunks naming either block honest, and a node that saw the other block then forwards a chunk the next hop finds inconsistent. Rejecting would penalise honest peers for the proposer's equivocation, and protects nothing the proof does not already: a chunk with a rewritten hint carries the same proof-bound bytes and is a distinct message. Dropping the field was considered, since the root leads to the bid and the bid to its block. It is kept because it lets a receiver that holds a chunk but not yet its block request the block by root instead of waiting for it.

**Why chunks are forwarded one by one, not "immediately".** The gain of chunking comes from a node passing on each chunk as it arrives instead of after the whole payload. The rule therefore says what must not happen, a chunk waiting for its siblings, and leaves the mechanism to the network layer. An earlier revision required a validated chunk to be "forwarded immediately". Read literally, that is a push of each chunk to every mesh peer in arrival order, which forbids forwarding by announcement, where a peer offers a chunk and sends it on request, and any choice of order or of targets; gossipsub already forwards by announcement to peers outside the mesh, and nodes that choose what to push and what to announce were, in simulation, faster and sent fewer bytes than full-mesh pushing. Nothing in this EIP depends on how a chunk reaches the next peer, only on its not waiting.

**Why `TOTAL_EXECUTION_PAYLOAD_CHUNKS = 64`.** The value is not derived from measurement; smaller chunk counts already show benefit compared to single large messages. 64 is chosen for forward compatibility in case we decide to extend protocol erasure coding via `c-kzg`, which segments data into 64 chunks and extends them to 128.

A fixed count fixes the chunk size only relative to the envelope: a 1 MiB envelope gives 16 KiB chunks, the size limit gives `MAX_PAYLOAD_CHUNK_SIZE`, and a 100 KiB envelope gives chunks of about 1.6 KiB, each carrying about 280 bytes of proof and fields. In simulations of segmented payload broadcast at today's payload sizes, latency reached its floor at a unit of about 16 KiB, and a fixed unit size held that floor across payload sizes where a fixed count did not; 64 matches that unit at 1 MiB. A fixed unit size with a count derived from the envelope length would spread the per-chunk overhead evenly, but needs the count committed in the bid, which the present tree does not do. See the open questions.

**Why unpadded `ByteList` chunks.** SSZ has no outer length prefix, so padding bytes would deserialize as envelope data; hashing each chunk's exact bytes commits its true length instead. Pinning the split and merkleization to SSZ lets two clients derive identical roots with existing code.

### Open questions and future considerations

- The networking scheme could be extended by erasure coding the chunks, so that a receiver can reconstruct the envelope from a subset of chunks. This introduces additional complexity and may lead to higher bandwidth usage. However, it may mitigate "coupon collector" problems, where a receiver missing a small number of chunks may wait a long time to receive them. In simulation, withholding a few plain chunks stranded every receiver, while a code of rate one half completed them all. Such an extension needs three things from this EIP's format: an index space beyond `TOTAL_EXECUTION_PAYLOAD_CHUNKS`, which gossip validation rejects today; the code's parameters bound by the commitment; and a decision on whether the committed bytes are the serialized envelope or a compressed form of it.
- Count against size. A fixed count gives chunks of a size proportional to the envelope (see the rationale). A target chunk size with a count derived from the envelope length needs the count committed in the bid and changes the shape of the commitment. Whether to make that change before the first deployment is open.
- The envelope's signature: which of the two ways in the Rationale is taken, dropping it or sending it on its own. The answer also decides what a reveal is for the payload timeliness committee and for fork choice.
- Recovery and storage. `ExecutionPayloadEnvelopesByRoot` serves signed envelopes that name their block. This EIP changes the envelope's gossip form without saying what a node stores and serves after reconstruction, or how a node that missed chunks obtains the payload after the slot: the whole envelope by root, or chunks by `(payload_chunks_root, index)`.
- In future it might be considered to introduce a `bal_chunks` topic following the same broadcasting scheme for Block Access List (BAL, [EIP-7928](./eip-7928.md)) messages, which are currently part of the execution payload. This would allow BAL message propagation to start sooner than the rest of the payload.
- Which blocks open the gate. Two options. (a) Any block the node has seen, whether it passed gossip validation or was processed, as a block fetched by root is: the chunks of a fetched block then flow, which is what the chunk's `beacon_block_root` hint is kept for, but a proposer that signs two blocks for a slot can make one node forward a set for each block it processes, which is slashable. (b) Only the first block a node sees for a proposer and slot, by either path: one set per proposer and slot at each node, but a node that saw one block first forwards no chunks for the other, even if the chain takes it. In the honest case they agree. This EIP specifies (a), with a slight preference.

## Backwards Compatibility

The `execution_payload` topic is removed and the execution bid gains a field, so this change is not backwards compatible and requires a fork.

## Security Considerations

Chunks are not individually signed; their authenticity derives from the signed block that carries the bid, via `payload_chunks_root`. Until the block is processed, the proposer's signature vouches for the root. Processing checks the builder's signature on the bid and that the builder can cover it; a self-build carries no builder signature and bids zero. The root carried in a chunk is unauthenticated on its own, but a chunk is only forwarded once the bid of a valid beacon block has committed to that root. A chunk whose proof fails against the root it carries is rejected at the first hop; a chunk under a root no block has named is held within the buffer bounds and never forwarded, so unsigned chunk spam costs each node a bounded amount of memory and no forwarding bandwidth.

`slot` and `beacon_block_root` are covered by neither the bid signature nor the inclusion proof, which is why the specification restricts their use to hints for windowing chunks and routing lookups. The consistency checks in gossip validation bound their misuse: a chunk replayed with a divergent `slot` is ignored unless that slot is current, and then finds no block for it naming its root, so it leaves the buffer unforwarded; a divergent `beacon_block_root` is ignored, not rejected, once the block containing the bid is seen: a peer may forward such a chunk honestly when the proposer has signed two blocks carrying the same bid, so a mismatch cannot be attributed to the sender. Because the chunk bytes are proof-bound, a message that differs only in these hint fields cannot alter the reconstructed envelope; because the message id covers the whole message, a copy with a rewritten hint, like a message with a garbage chunk or proof under the honest root and index, is a distinct message that neither stands in for the honest one nor occupies its id in the seen cache; and because the first-seen tuple is recorded only on acceptance, the honest copy is still accepted when it arrives.

Per-index equivocation is not possible: two distinct chunks that both verify at the same `(payload_chunks_root, index)` would imply a collision in the Merkle tree, so at most one chunk per index can propagate for a given commitment.

The `chunk.index` bound is load-bearing: `is_valid_merkle_branch` reads only the low `CHUNK_INCLUSION_PROOF_DEPTH` bits, so an unbounded index would let the same chunk propagate again at `index + k * TOTAL_EXECUTION_PAYLOAD_CHUNKS`.

Pre-block buffering is bounded per root and per peer, and a chunk enters it only after its inclusion proof has been checked against the root it carries. A peer can fill its own reservation with chunks under roots no block will name, and nothing else: the reservation keeps it from displacing another peer's copies, and every buffered chunk is dropped at the end of its slot. A proposer that signs two blocks for one slot, each naming a different root, causes both chunk sets to be forwarded; the equivocation is slashable, and the `beacon_block` topic forwards only the first block per proposer per slot.

Gossip validity of a chunk does not imply validity of the reconstructed envelope; full envelope validation still happens after reconstruction, as under [EIP-7732](./eip-7732.md), with two differences this EIP has to own. The reconstructed envelope carries no builder signature and names no block. Today every consumer of a reveal takes the signed envelope: envelope gossip, fork choice when it stores the payload under its block root, the payload timeliness committee's `payload_present` vote, and recovery by root. Under this EIP as written, a reveal is a reassembled envelope that verifies under the root a block's bid commits to, anyone who holds the bytes can complete it, and the same chunks complete the payload for every block that carries that bid. What each consumer takes instead of the signed envelope is not yet specified; the Rationale discusses the two ways to settle it.
