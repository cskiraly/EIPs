## Abstract

[EIP-7732](./eip-7732.md) propagates the execution payload as a single message on the `execution_payload` gossipsub topic. This EIP replaces that topic with two: `execution_payload_chunks`, which carries the envelope's body, the payload and the execution requests, split into chunks, and `execution_payload_signature`, which carries the builder's signature over the envelope on its own. The builder commits to the chunk set in the execution bid with a descriptor, holding a chunking scheme, the chunk count, the chunk size and a Merkle root over the chunks, so each chunk is independently verifiable from a single block signature check plus an inclusion proof. This EIP defines one scheme, which splits the body into chunks of 16 KiB. Consensus fixes only the descriptor's shape, so later schemes, an erasure code for instance, need no fork. After reassembly a node holds the same `SignedExecutionPayloadEnvelope` as today, so nothing downstream of gossip changes.

## Motivation

The gas-limit growth that [EIP-7732](./eip-7732.md) enables implies larger payloads leading to increased latency. If Payload Timeliness Committee (PTC) members do not receive the payload within the attestation deadline, an otherwise valid payload is considered missed.

The existing `execution_payload` gossipsub topic scales poorly as payloads grow. Two effects dominate:

1. Once a peer has received a large message, it is hard to cancel in-flight duplicates, so the same bytes arrive several times and consume bandwidth that could carry new data.
2. A peer must download the full message before it can forward any of it, so each hop adds a full transfer, leading to increased latency proportional to message size multiplied by hop count.

Both effects are mitigated when the message is chunked. Large duplicates are impossible with chunk granularity, and a peer can forward each chunk as soon as it arrives, so hops overlap instead of serializing.

### Parameters

| Constant | Value |
| --- | --- |
| `MAX_PAYLOAD_CHUNK_SIZE` | `2**18` (262,144 bytes) |
| `MAX_EXECUTION_PAYLOAD_CHUNKS` | `2**11` (2,048) |
| `CHUNK_INCLUSION_PROOF_DEPTH` | `ceillog2(MAX_EXECUTION_PAYLOAD_CHUNKS)` (11) |
| `CHUNKING_SCHEME_PLAIN` | `ChunkingScheme(0)` |
| `PLAIN_CHUNK_SIZE` | `2**14` (16,384 bytes) |

The first three constants are the limits of the format, within which every chunking scheme works: the largest chunk, the number of chunk indices, and with it the depth of a chunk's inclusion proof. They bound the `PayloadChunk` message, so changing them changes the message. `PLAIN_CHUNK_SIZE` belongs to the one scheme this EIP defines. `MAX_PAYLOAD_SIZE`, the networking specification's limit on an uncompressed gossip message, bounds the serialized body. At that limit the plain scheme splits a body into `MAX_PAYLOAD_SIZE // PLAIN_CHUNK_SIZE` (640) chunks. The index space holds more than three times as many, and the largest chunk the format allows is larger than a sixty-fourth of the limit, so a scheme with 64 chunks fits at every size.

### Custom types

| Name | SSZ equivalent | Description |
| --- | --- | --- |
| `ChunkIndex` | `uint64` | Index of a chunk within its set, `0` through `chunk_count - 1` |
| `Chunk` | `ByteList[MAX_PAYLOAD_CHUNK_SIZE]` | One piece of the chunked body; under the plain scheme, a contiguous slice of the serialized `ExecutionPayloadBody` |
| `ChunkingScheme` | `uint8` | Identifies how the body is split into chunks and reconstructed |

### Commitment

The execution bid commits to the chunked body with a descriptor:

```python
class PayloadChunksDescriptor(Container):
    scheme: ChunkingScheme
    chunk_count: uint64
    chunk_size: uint64
    chunks_root: Root


class ExecutionPayloadBid(ProgressiveContainer):
    ACTIVE_FIELDS = active_fields(width=13)  # [Modified in this EIP]

    ...
    execution_requests_root: Root
    payload_chunks: PayloadChunksDescriptor  # [New in this EIP]
```

The descriptor holds what a forwarding node checks without knowing the scheme: `chunk_count`, the number of chunks; `chunk_size`, the length of every chunk but the last, which is not longer; and `chunks_root`, the SSZ `hash_tree_root` of the `Vector[Bytes32, MAX_EXECUTION_PAYLOAD_CHUNKS]` whose first `chunk_count` elements are the SHA-256 hashes of the chunks and whose other elements are zero. `scheme` names how the builder derives the chunks from the body and how a receiver reconstructs the body from them; this EIP defines one scheme, `CHUNKING_SCHEME_PLAIN`, whose derivation is `compute_payload_chunks_descriptor` in the Chunking section. Anything else a scheme needs travels inside the chunks, under the root.

Consensus fixes only the descriptor's fields and their types. Which schemes a node implements, the values each scheme allows and the format's limits are networking rules, applied in gossip validation. A scheme's rules, the values its descriptors may hold and how its chunks are derived and reassembled, are fixed when its identifier is assigned: a changed rule is a new identifier, so every node that implements a scheme applies the same rules. The format's limits change only with a new version of the `PayloadChunk` message and its topic. A descriptor is valid when its scheme is one the node implements and its values are within the format's limits and allowed by that scheme:

```python
def is_known_chunking_scheme(scheme: ChunkingScheme) -> bool:
    return scheme == CHUNKING_SCHEME_PLAIN


def compute_plain_chunk_count(length: uint64) -> uint64:
    return (length + PLAIN_CHUNK_SIZE - 1) // PLAIN_CHUNK_SIZE


def is_valid_payload_chunks_descriptor(descriptor: PayloadChunksDescriptor) -> bool:
    if not is_known_chunking_scheme(descriptor.scheme):
        return False
    if not (
        0 < descriptor.chunk_count <= MAX_EXECUTION_PAYLOAD_CHUNKS
        and 0 < descriptor.chunk_size <= MAX_PAYLOAD_CHUNK_SIZE
    ):
        return False
    # CHUNKING_SCHEME_PLAIN
    return (
        descriptor.chunk_size == PLAIN_CHUNK_SIZE
        and descriptor.chunk_count <= compute_plain_chunk_count(MAX_PAYLOAD_SIZE)
    )
```

A bid whose descriptor is not valid commits to nothing: no chunk is forwarded under it (see Gossip validation). A proposer SHOULD NOT include such a bid in its block. A receiver therefore verifies one block signature, per chunk one Merkle inclusion proof and one length, and once per payload the envelope's signature, which arrives on its own (see Signature). The checks that a gossiped envelope passes today against the block and its bid are made on the reconstructed envelope (see Reconstruction and the reveal).

### Body

Chunking is applied to the envelope's body, the two fields of the Gloas `ExecutionPayloadEnvelope` that the block does not determine:

```python
class ExecutionPayloadBody(Container):
    payload: ExecutionPayload
    execution_requests: ExecutionRequests
```

The envelope's other fields are determined by the block that carries the bid: `builder_index` by the bid, `beacon_block_root` by the block's root, `parent_beacon_block_root` by its parent root. A receiver rebuilds the envelope from the body and the block (see Reconstruction and the reveal); the `ExecutionPayloadEnvelope` container is unchanged. The serialized bytes of the body are what the commitment covers.

Under [EIP-7732](./eip-7732.md) the builder constructs the envelope after observing that its bid was included, and can therefore embed the beacon block root. Under this EIP the builder commits to the chunks when it produces the bid, before the block exists, so what it commits to is the body, which it holds then. The block root is instead carried per chunk in the `PayloadChunk` message, as a hint, together with `payload_chunks_root`, the descriptor's `chunks_root`:

```python
class PayloadChunk(Container):
    payload_chunks_root: Root
    index: ChunkIndex
    chunk: Chunk
    chunk_inclusion_proof: Vector[Bytes32, CHUNK_INCLUSION_PROOF_DEPTH]
    slot: Slot
    beacon_block_root: Root
```

`payload_chunks_root` equals `chunks_root` of the bid's descriptor and identifies the chunk set. A receiver verifies the inclusion proof against it as soon as the chunk arrives, and forwards the chunk once a valid beacon block for the slot has named this root in its bid.

`slot` and `beacon_block_root` sit outside the inclusion proof and are unauthenticated hints: `slot` allows windowing a chunk cheaply and MUST equal the slot of a bid committing to `payload_chunks_root`, while `beacon_block_root` lets a receiver locate or request the corresponding beacon block and MUST equal the root of the block containing that bid. Receivers MUST NOT treat either field as authenticated and MUST use them only as hints: to window a chunk and to route lookups; a chunk is bound to a bid solely through `payload_chunks_root`.

### Signature

The builder signs the envelope as under [EIP-7732](./eip-7732.md): the Gloas `ExecutionPayloadEnvelope` for the block that carries its bid, `beacon_block_root` included. The signature cannot travel inside the chunks, whose commitment the bid made before the block existed; it travels on its own:

```python
class ExecutionPayloadEnvelopeSignature(Container):
    slot: Slot
    beacon_block_root: Root
    payload_root: Root
    signature: BLSSignature
```

`signature` is `SignedExecutionPayloadEnvelope.signature`, unchanged. `payload_root` is `hash_tree_root(envelope.payload)`. `beacon_block_root` names the block the envelope was signed for; `slot` is an unauthenticated hint, as in the chunk.

A receiver verifies the signature before it holds the payload. Every field of the envelope but the payload is determined by the block: `execution_requests` by the bid's `execution_requests_root`, `builder_index` by the bid, `beacon_block_root` by the block's root and `parent_beacon_block_root` by its parent root. SSZ computes a container's root from its fields' roots, so the envelope's root follows from `payload_root` and the block through a header whose root is the envelope's, as `BeaconBlockHeader`'s is `BeaconBlock`'s; the header's kind and active fields are the envelope's, which is what makes the roots equal:

```python
class ExecutionPayloadEnvelopeHeader(ProgressiveContainer):
    ACTIVE_FIELDS = active_fields(width=5)

    payload_root: Root
    execution_requests_root: Root
    builder_index: BuilderIndex
    beacon_block_root: Root
    parent_beacon_block_root: Root


def verify_execution_payload_envelope_signature_message(
    state: BeaconState,
    block: BeaconBlock,
    message: ExecutionPayloadEnvelopeSignature,
) -> bool:
    bid = block.body.signed_execution_payload_bid.message
    header = ExecutionPayloadEnvelopeHeader(
        payload_root=message.payload_root,
        execution_requests_root=bid.execution_requests_root,
        builder_index=bid.builder_index,
        beacon_block_root=message.beacon_block_root,
        parent_beacon_block_root=block.parent_root,
    )
    if bid.builder_index == BUILDER_INDEX_SELF_BUILD:
        pubkey = state.validators[block.proposer_index].pubkey
    else:
        pubkey = state.builders[bid.builder_index].pubkey
    signing_root = compute_signing_root(header, get_domain(state, DOMAIN_BEACON_BUILDER))
    return bls.Verify(pubkey, signing_root, message.signature)
```

`state` is the post-state of the block, as in `verify_execution_payload_envelope_signature`, whose key and domain this function reuses. A signature that verifies here is the builder's signature over an envelope for this block whose payload has root `payload_root`; whether that payload is the committed one is known on reassembly.

### Chunking

The builder MUST derive the chunks, and therefore the descriptor, as its scheme specifies. Under `CHUNKING_SCHEME_PLAIN`, every chunk but the last is `PLAIN_CHUNK_SIZE` bytes long; the last holds the remainder and is never empty. No padding is added.

```python
def compute_payload_chunks(
    body: ExecutionPayloadBody,
) -> List[Chunk, MAX_EXECUTION_PAYLOAD_CHUNKS]:
    data = ssz_serialize(body)
    chunk_count = compute_plain_chunk_count(len(data))
    chunks = []
    for i in range(chunk_count):
        start = i * PLAIN_CHUNK_SIZE
        chunks.append(Chunk(data[start:start + PLAIN_CHUNK_SIZE]))
    return chunks


def compute_payload_chunks_descriptor(
    body: ExecutionPayloadBody,
) -> PayloadChunksDescriptor:
    chunks = compute_payload_chunks(body)
    leaves = [hash(chunk) for chunk in chunks]
    leaves += [Bytes32()] * (MAX_EXECUTION_PAYLOAD_CHUNKS - len(leaves))
    return PayloadChunksDescriptor(
        scheme=CHUNKING_SCHEME_PLAIN,
        chunk_count=len(chunks),
        chunk_size=PLAIN_CHUNK_SIZE,
        chunks_root=hash_tree_root(Vector[Bytes32, MAX_EXECUTION_PAYLOAD_CHUNKS](leaves)),
    )
```

Each leaf is `hash(chunk)`, the SHA-256 hash of the chunk's bytes; `chunk_inclusion_proof` is the SSZ Merkle branch of leaf `index` in the `Vector`. The builder sets the leaves past `chunk_count` to zero. No receiver checks this: it is the index bound in gossip validation that ignores a chunk at an index the set does not have. The proof is verified as follows:

```python
def verify_payload_chunk_inclusion_proof(payload_chunk: PayloadChunk) -> bool:
    return is_valid_merkle_branch(
        leaf=hash(payload_chunk.chunk),
        branch=payload_chunk.chunk_inclusion_proof,
        depth=CHUNK_INCLUSION_PROOF_DEPTH,
        index=payload_chunk.index,
        root=payload_chunk.payload_chunks_root,
    )
```

The length a chunk must have follows from the descriptor, whatever the scheme:

```python
def is_valid_chunk_length(
    descriptor: PayloadChunksDescriptor,
    index: ChunkIndex,
    length: uint64,
) -> bool:
    if index + 1 < descriptor.chunk_count:
        return length == descriptor.chunk_size
    return 0 < length <= descriptor.chunk_size
```

Under the plain scheme, receivers concatenate chunks `0` through `chunk_count - 1` and deserialize the result as an `ExecutionPayloadBody`; nothing is stripped, since each leaf hashes its chunk's exact bytes.

### Networking

This EIP introduces two gossip topics and removes `execution_payload`: `execution_payload_chunks` carries `PayloadChunk` messages and `execution_payload_signature` carries `ExecutionPayloadEnvelopeSignature` messages.

On the `execution_payload_bid` topic, two validations are added to those of [EIP-7732](./eip-7732.md), before the bid's signature check, with `bid = signed_execution_payload_bid.message`:

- _[IGNORE]_ The node implements the bid's chunking scheme: `is_known_chunking_scheme(bid.payload_chunks.scheme)`.
- _[REJECT]_ The descriptor is valid: `is_valid_payload_chunks_descriptor(bid.payload_chunks)`. A node applies this check only to a scheme it implements.

A bid with a scheme the node does not implement is ignored rather than rejected, so that a node that has not yet adopted a scheme does not penalise the peers that have.

The descriptor adds 49 bytes to the bid, so `MAX_SIGNED_EXECUTION_PAYLOAD_BID_SIZE`, the networking specification's bound on a `SignedExecutionPayloadBid`, becomes `Uint64(196981)`.

Once the builder has successfully processed a beacon block containing its bid, it SHOULD construct the `chunk_count` `PayloadChunk` messages and publish them on `execution_payload_chunks`, and sign the envelope for that block and publish the `ExecutionPayloadEnvelopeSignature` on `execution_payload_signature`; it SHOULD NOT publish either until it has successfully processed that block. As under Gloas's rule for an honestly withheld payload, it MAY withhold both when the block was not timely and is therefore not the head of its chain. The two are published in no particular order; a receiver acts once it holds both.

Messages on both topics use the `message-id` of the Altair networking specification, the hash of the topic and the uncompressed message. A chunk that passes validation has one byte form per block: `payload_chunks_root`, `index`, `chunk` and `chunk_inclusion_proof` are fixed by the commitment, and `slot` and `beacon_block_root` by the block that validation checks them against. Every node's copy of a chunk is therefore the same gossipsub message, and duplicate suppression, `IHAVE` and `IWANT`, and `IDONTWANT` name a chunk by that id with no rule of this EIP. The id is not derived from the commitment; the Rationale says why.

#### Seen cache

The `Seen` cache used by the gossip validation functions is extended to track received chunks:

```python
@dataclass
class Seen:
    ...
    payload_chunk_tuples: set[tuple[Root, ChunkIndex]]  # [New in this EIP]
    execution_payload_signatures: set[Root]  # [New in this EIP]
```

`payload_chunk_tuples` records the `(payload_chunks_root, index)` pair of every accepted chunk, analogous to `data_column_sidecar_tuples` for column sidecars, and backs the first-seen check below. `execution_payload_signatures` records the block root of every accepted signature message. The Gloas entries `execution_payload_envelopes` and `execution_payloads`, which gossip validation of the removed topic filled, are filled at the reveal (see Reconstruction and the reveal).

#### Gossip validation

The following validations MUST pass before a node forwards a `PayloadChunk` `chunk` on the topic.

- _[IGNORE]_ `chunk.slot` equals the current slot, within `MAXIMUM_GOSSIP_CLOCK_DISPARITY` allowance.
- _[REJECT]_ `chunk.index` is less than `MAX_EXECUTION_PAYLOAD_CHUNKS`.
- _[REJECT]_ The inclusion proof is valid as verified by `verify_payload_chunk_inclusion_proof(chunk)`.
- _[IGNORE]_ The node has seen a valid beacon block for `chunk.slot` whose bid commits to `chunk.payload_chunks_root`: the bid's `payload_chunks` descriptor is valid and its `chunks_root` equals `chunk.payload_chunks_root`. A chunk that fails only this check MUST be buffered as described below and revalidated when such a block is seen.
- _[IGNORE]_ `chunk.beacon_block_root` is the root of such a block.
- _[IGNORE]_ `chunk.index` is less than `chunk_count` of that block's descriptor.
- _[IGNORE]_ The chunk's length fits that block's descriptor, as checked by `is_valid_chunk_length` for `chunk.index` and `len(chunk.chunk)`.
- _[IGNORE]_ `(chunk.payload_chunks_root, chunk.index)` is not present in `seen.payload_chunk_tuples` (first-seen per commitment and index); the tuple is added upon acceptance.

A beacon block is seen once it has passed gossip validation on the `beacon_block` topic, or once it has been processed, as a block fetched by root is; gossip validation alone is enough. Validation and forwarding of a chunk MUST NOT wait for the other chunks of its set: a chunk that passes these validations is forwarded on its own, whether pushed or announced, and kept until the envelope can be reconstructed.

#### Gossip validation of the signature

The following validations MUST pass before a node forwards an `ExecutionPayloadEnvelopeSignature` `message` on the topic.

- _[IGNORE]_ `message.slot` equals the current slot, within `MAXIMUM_GOSSIP_CLOCK_DISPARITY` allowance.
- _[IGNORE]_ The node has not accepted a signature message for this block: `message.beacon_block_root` is not in `seen.execution_payload_signatures`; the root is added upon acceptance.
- _[IGNORE]_ The block with root `message.beacon_block_root` has been processed, so that its post-state is available. A message that fails only this check MUST be buffered as described below and revalidated when the block is processed.
- _[REJECT]_ `message.slot` equals the block's slot.
- _[REJECT]_ The signature is valid as verified by `verify_execution_payload_envelope_signature_message(state, block, message)`.

The signature message is verified against the block's post-state because the builder's key and the signing domain come from it, as they do for a gossiped envelope today. The chunks do not wait for it: a node that holds the chunks and the block holds the bytes, and relays them, whether or not it holds the signature.

#### Buffering before the block

A chunk whose block is not yet seen MUST be held in a buffer. The buffer is divided among the peers that send chunks, so one peer's chunks cannot displace another's; within a peer's share, each `payload_chunks_root` holds at most `MAX_PAYLOAD_SIZE` bytes and `MAX_EXECUTION_PAYLOAD_CHUNKS` chunks. Only chunks that have passed the slot, index and inclusion proof checks above enter the buffer. A chunk that does not fit its sender's share is dropped, and its message id MUST NOT remain marked as seen, so that a copy of the same chunk from another peer is validated when it arrives. Buffered chunks are revalidated when a valid beacon block for their slot is seen, and one that passes is forwarded as if it had passed on arrival; the rest are dropped at the end of their slot (within `MAXIMUM_GOSSIP_CLOCK_DISPARITY`). A signature message whose block is not yet processed is held under the same per-peer reservation, revalidated when the block is processed, and dropped at the same time; until then it costs its 168 bytes and no verification.

#### Reconstruction and the reveal

A node that holds all `chunk_count` chunks of the set a block's bid commits to reconstructs the body (see Chunking) and, from the body and the block, the envelope:

```python
def reconstruct_execution_payload_envelope(
    body: ExecutionPayloadBody,
    block: BeaconBlock,
) -> ExecutionPayloadEnvelope:
    bid = block.body.signed_execution_payload_bid.message
    return ExecutionPayloadEnvelope(
        payload=body.payload,
        execution_requests=body.execution_requests,
        builder_index=bid.builder_index,
        beacon_block_root=hash_tree_root(block),
        parent_beacon_block_root=block.parent_root,
    )
```

The envelope MUST pass the checks that gossip validation of a `SignedExecutionPayloadEnvelope` makes today against the block and its bid, less the ones its construction settles: `payload.slot_number` equals the block's slot, `payload.block_hash` equals the bid's, the execution requests' root equals the bid's `execution_requests_root`, and the request and withdrawal limits hold.

A node that holds such an envelope and an accepted signature message for the block with `payload_root` equal to `hash_tree_root(envelope.payload)` holds `SignedExecutionPayloadEnvelope(message=envelope, signature=message.signature)`, with its signature verified. It records the envelope as seen and stores its payload in `seen`, as gossip validation of the `execution_payload` topic did, and from here on nothing changes: fork choice's `on_execution_payload_envelope`, the payload timeliness committee's `payload_present` vote and recovery by `ExecutionPayloadEnvelopesByRoot` take that object as they do today. Where the Gloas specification says that a `SignedExecutionPayloadEnvelope` was seen before some time, it is read as held before that time.

If `payload_root` differs from the reassembled payload's root, the builder signed a payload other than the one it committed to, and the node holds no signed envelope; neither message is at fault at the gossip layer, and neither sender is penalised. A node that holds the chunks but not the signature, or the signature but not every chunk, requests the whole `SignedExecutionPayloadEnvelope` by root, as a node missing an envelope does today. A node that holds the signed envelope stores and serves it as today.

## Rationale

**Why a Merkle commitment.** Alternatives such as KZG place proof generation on the builder's critical path. A Merkle tree over chunks is cheap enough to build at bid time, and a single root in the bid makes each chunk self-verifying against one already-verified signature.

**Why the root travels in the chunk.** `payload_chunks_root` in the message carries no authority of its own. It lets a receiver verify the inclusion proof the moment the chunk arrives, and key its buffer and the first-seen check by the set the chunk claims to belong to, before the block that names that set has arrived. A chunk whose proof fails against the root it carries is rejected at the first hop; a root no block has named authenticates nothing. `slot` and `beacon_block_root` are hints for the same reason: they help a receiver find the block, and the consistency checks in gossip validation are all that holds them to it.

**Why the message id is the content id.** An id computed from `payload_chunks_root` and `index` alone was considered. A node could then compute the id of every chunk of a set from the bid, request exactly the chunks it lacks when they are announced, decline announced ids under roots it cannot authenticate, and tell its peers which chunks it holds. It was rejected because of how gossipsub implementations treat ids. For example, go-libp2p-pubsub records an id as seen before the application's validator runs and keeps it seen whatever the validator decides; later copies received from peers are dropped as duplicates and are not requested when announced. With an id anyone can compute from public data, and the root and the index are public once the block is, a peer could send a garbage message under the honest chunk's id ahead of the chunk itself and have the honest chunk refused as a duplicate at every node its garbage reached first, for the rest of the slot. The content id has no such weakness: a message that differs from the honest chunk in any byte has another id, so no peer can occupy the honest chunk's id. And since every byte of a valid chunk is fixed by the commitment and the block, the content id names the chunk as well as a computed one would for every node that holds it. What the computed id would have added, requests by index for chunks a node has never seen announced, needs an announcement protocol that decides for itself when an id counts as seen, and is outside this EIP.

**Why a chunk waits for its block.** A chunk is forwarded only once a valid beacon block for its slot has named its root. The block is the one object that says which bid was chosen. Gossip validation accepts only the first block per proposer and slot, but additional processed blocks can open the gate for additional chunk sets at the same node; producing those blocks is slashable equivocation (see Security Considerations and the open questions). Processing the block then checks that the bid is signed and funded, or is a self-build of zero value; whether the builder pays follows Gloas's settlement rules. The wait costs less than it appears. The gate needs only the descriptor in the bid, which is in the body of any signature-valid block, so it opens on gossip validation of the block, not on processing it. Along a path the wait is usually paid once, at the first node the chunks reach before the block; a downstream node has usually had the block for as long as its upstream did, less one link, so it does not wait again. Blocks and chunks travel on different topics and meshes, so a node can still receive a chunk first and wait.

Four alternatives were considered.

_Forwarding against any accepted bid._ An earlier revision of this EIP forwarded a chunk as soon as a bid accepted on the bid topic had committed to its root, so that no node would wait for the block. Bid gossip accepts one bid per builder and parent per slot, and a bid that is not chosen costs its builder nothing, so every accepted bid could put a full chunk set on the network for free. It also let a payload travel ahead of its block: a builder that also controls the proposer could release the payload while holding the block back. Reviewers of that revision asked how a node would know that a gossiped bid was the chosen one; it cannot, and the block is what says so.

_Waiting for the block to be processed._ Gating on a processed block, as the `execution_payload` topic does today, makes the anchor exactly as strong as the receiver's own state transition, but adds its latency to the wait at the first node, and the root does not need it: it is read from the block body once the proposer's signature is valid. The equivocation this admits is discussed under Security Considerations. A block that passes gossip validation but fails processing, over a forged bid or for any other reason, still opens the gate for its set, so nodes can forward chunks for a block they then discard; today they forward no envelope for such a block. If it is the proposer's only block for the slot, the proposer loses the slot; a second block would be a slashable equivocation. The chunks of such a block can come from its builder, if the builder publishes before processing the block (see Networking), or from anyone who holds them, forwarded under that block's hints.

_Checking the bid's signature at the gate._ Each node could also verify the builder's signature on the bid, once per block, reusing the check if the bid already passed the bid topic; a self-build has no such signature and would stay exempt. That keeps forged bids out, but not a block that fails processing for another reason, such as an unfunded bid, a wrong state root or an invalid attestation. For a bid from an external builder whose signature is not already verified, it can delay forwarding where chunks arrive before their block; it does not prevent a proposer from equivocating to authorize additional sets, including at a node that processes the additional blocks.

_A fast lane for roots seen on the bid topic._ Chunks whose root belongs to a bid accepted on the bid topic could be exempt from the per-peer share of the buffer, since their set is already bounded by bid validation. This was rejected because it favours builders that bid through the topic over a proposer that builds its own payload, whose root never appears there: the two would meet different buffer rules at the same node for the same kind of message.

Chunks that arrive before their block are buffered rather than dropped. The objection that a buffer of unauthenticated data is a denial-of-service surface is met by bounds rather than by refusal: the inclusion proof is checked against the carried root before a chunk enters, each peer has a share of its own, and a share holds at most one set per root, so one peer's chunks cannot displace another's. Dropping instead would cost the self-building proposer most, since its block and its chunks travel on different topics and the chunks overtake the block at the nodes nearest the source. A gossip layer that records a message as seen before validating it, as go-libp2p-pubsub does, makes any drop last: a dropped chunk is refused as a duplicate from every other peer and is not requested when announced, until the seen cache forgets it, which takes longer than the slot. A peer whose share is full could even deliver an honest chunk first, to have it dropped and its id kept. This is why a chunk dropped for lack of room must not stay marked as seen. Where a gossip layer cannot yet do that, a stopgap is to size each share to hold one full set, `MAX_PAYLOAD_SIZE`, and to accept that a peer that delivers a chunk first can make the node lose it for the slot, to be recovered with the envelope by root.

A chunk accepted on revalidation is forwarded as a first delivery would be. A node can meet that by deferring its validator's result until the block arrives, which keeps the message pending in the gossip layer, or by reporting IGNORE and publishing the chunk again once it passes, which needs a gossip layer that forwards a publish of an id it has seen but not delivered (go-libp2p-pubsub does since v0.17.0). This EIP fixes the outcome, not the mechanism.

**Why the signature travels on its own.** This EIP chunks the envelope's body, not the `SignedExecutionPayloadEnvelope`: the bid commits to the chunks before the block exists, and the signature covers the block's root, so it cannot be under the commitment. It is still needed. The commitment authenticates the bytes, but the signature is what makes a reveal the builder's act. Today every consumer of a reveal takes the signed envelope, envelope gossip, fork choice when it stores the payload under its block root, the payload timeliness committee's `payload_present` vote and recovery by root, and only the builder, or the proposer when self-building, can produce it. Sending the ordinary signature as its own message keeps all of that as it is: after reassembly a node holds the same object as today, and the consensus specification changes in nothing but the gossip that delivers it. The cost is one more message per payload, and a reveal that waits for two parts instead of one. Five alternatives were considered.

_Dropping the signature._ A payload would count as revealed once it is reassembled from chunks that verify under the root the block's bid commits to, and fork choice, the payload timeliness committee and recovery by root would be respecified to take that object. This changes what a reveal is. The builder loses exclusive control over revealing, since anyone holding the bytes can complete the reveal, a reveal can no longer be made for one block and withheld from another carrying the same bid, and a partial release has made most of the transactions public without revealing anything. It is a consensus change beyond what chunking needs.

_A new release object._ The builder could sign a short statement over the block root instead of the envelope, which verifies without any root of the payload. But the rebuilt envelope would then carry no valid signature, and every consumer listed above would have to accept the new object in its place; keeping both signatures avoids that at the price of a second signing and a second message. More change than the envelope's own signature, for no gain.

_The signature inside the chunks._ The ordinary signature, with `payload_root`, could ride in every chunk or in some of them: 128 bytes per chunk that carries it, under one percent of a 16 KiB chunk. It removes the dependence on a second message arriving, and it is a transport choice that can be added to the separate message rather than a different design. It is left out here so that the chunk message stays what the commitment covers plus its hints; a later revision may add it.

_The envelope's root instead of the payload's._ A message carrying the envelope's root would verify any signature the builder ever made over any envelope, since the signing domain does not change from slot to slot; an old signature relayed under a new block root would pass and take the block's first-seen slot. Carrying the payload's root makes the receiver compute the envelope's root from the block itself, so a signature verifies only for the block it was made for. Every other field root is the block's, which is what makes the header's root the envelope's.

_A gossip-valid block instead of a processed one._ The builder's key and the signing domain come from the block's post-state, as for a gossiped envelope today. The parent's state would serve on every slot but the first of a fork, and the saving is small against the chunks' transfer, so the rule mirrors the existing one. The chunks are not held for it.

**Why the body is what is split.** The chunks carry what the block does not determine: the payload and the execution requests. The envelope's other three fields are the bid's builder index, the block's root and its parent's, which every receiver has from the block before it forwards a chunk, and the signature covers the envelope the receiver rebuilds from both. An earlier revision chunked the envelope itself with `beacon_block_root` left inactive, to stay as close as possible to the object the builder signs. It was replaced because the rebuilt envelope is the signed object either way, so the modified container bought nothing, and because it changed a consensus container where none needs changing; the body is a type of this EIP alone.

**Why a wrong `beacon_block_root` is ignored, not rejected.** The field is a lookup hint outside the proof, and a mismatch has honest causes: a proposer who signs two blocks with the same bid makes chunks naming either block honest, and a node that saw the other block then forwards a chunk the next hop finds inconsistent. Rejecting would penalise honest peers for the proposer's equivocation, and protects nothing the proof does not already: a chunk with a rewritten hint carries the same proof-bound bytes and is a distinct message. Dropping the field was considered, since the root leads to the bid and the bid to its block. It is kept because it lets a receiver that holds a chunk but not yet its block request the block by root instead of waiting for it.

**Why chunks are forwarded one by one, not "immediately".** The gain of chunking comes from a node passing on each chunk as it arrives instead of after the whole payload. The rule therefore says what must not happen, a chunk waiting for its siblings, and leaves the mechanism to the network layer. An earlier revision required a validated chunk to be "forwarded immediately". Read literally, that is a push of each chunk to every mesh peer in arrival order, which forbids forwarding by announcement, where a peer offers a chunk and sends it on request, and any choice of order or of targets; gossipsub already forwards by announcement to peers outside the mesh. Nothing in this EIP depends on how a chunk reaches the next peer, only on its not waiting.

**Why a chunking descriptor in the bid.** Only the descriptor's shape is part of consensus: its fields and their types are hashed into the block, so changing them takes a fork, while consensus never checks its values. This EIP changes the bid anyway, so it fixes the descriptor now, with the fields any scheme needs a forwarding node to check: the count, the chunk size and the root. A node reads the count to bound the index and to know when a set is complete, and the size to check each chunk's length before forwarding it and to know, once the block is seen, how much memory a set can take. Everything else a scheme needs, the parameters of a code or where a section of the data ends, travels inside the chunks under the root. A later scheme then changes values, not the bid, and is introduced by client releases.

Schemes can differ in how the count and the size follow from the payload: a fixed count, a fixed size, or either chosen per payload. They can add parity chunks for an erasure code, compress the body before splitting it, or lay out the data differently, for instance with the block access list first. A scheme whose chunks vary in size, to align them with transactions for instance, would also change the length rule, which is a networking rule too. What no scheme changes is how a chunk is proven: the tree, its hash and its depth are part of the message.

_The values under the root._ The descriptor's values could instead be committed under the root, with each chunk carrying them. That would keep a single root in the bid and let a node check a chunk's length before its block arrives. It was rejected because the bid is what a proposer chooses: with the values in the bid, a proposer, and the bid topic, can pass over a scheme the network does not implement yet, whereas under the root such a scheme would surface only after the block, as a slot without a payload. The earlier length check it would allow matters little: until the block, the format's chunk bound limits what a chunk can cost.

_An SSZ `List`._ A `List` would commit the count a second time, in its root, and would add a level to every proof. The descriptor already commits the count, so the tree is a `Vector` of fixed size: its proof depth is constant, and clients derive roots and branches with existing SSZ code.

**Why the plain scheme fixes the chunk size.** The chunk size is what the latency of chunked broadcast depends on, so the plain scheme fixes it and lets the count follow from the body's length. Simulations of segmented payload broadcast at today's payload sizes, run by one of the authors, found that latency reached its floor at a chunk size of about 16 KiB, and that a fixed chunk size held that floor across payload sizes, while the per-chunk cost, about 440 bytes of proof and fields per message under this format, grows with the count. That cost is under 3 percent of a 16 KiB chunk.

_A fixed count._ An earlier revision fixed the count at 64 and let the chunk size follow the envelope: 16 KiB at 1 MiB, 160 KiB at the size limit, and at 100 KiB about 1.6 KiB, each with about 280 bytes of proof and fields. It chose 64 to leave room for an erasure code from `c-kzg`, which extends the 64 cells of a blob to 128. Under this EIP a fixed count is a scheme the format can express, since the largest chunk it allows is larger than a sixty-fourth of the size limit. The plain scheme fixes the size instead, because the size is what the latency depends on; a code from `c-kzg` would be a scheme of its own (see the open questions).

**Why a scheme identifier.** The scheme says how the builder derived the chunks from the body and how a receiver reconstructs the body. A later scheme changes the derivation, the reconstruction and the values a descriptor may hold, and at most the length rule (see above): not the message, and not the bid's shape. Two schemes can also serve at once, chosen per payload, say a code below some size and plain chunks above it. Adding a scheme is a networking change, not a fork, since consensus does not check the scheme. Nodes have to implement a scheme before builders use it: a node that cannot reassemble a payload holds it late, if at all, and a member of the payload timeliness committee in that position votes the payload absent. Builders, whose payloads would count as late, have every reason to wait. A node that does not implement a scheme ignores its bids and chunks rather than rejecting them, so that during a rollout the nodes that have not upgraded do not penalise the peers that have. The identifier costs one byte per bid. Tying the scheme to the fork version was considered and rejected: it fixes one scheme per fork, so two could not coexist, and every change to the chunking would go through the fork schedule.

**Why unpadded `ByteList` chunks.** SSZ has no outer length prefix, so padding bytes would deserialize as body data; hashing each chunk's exact bytes commits its true length instead. Pinning the split and merkleization to SSZ lets two clients derive identical roots with existing code.

### Open questions and future considerations

- The networking scheme could be extended by erasure coding the chunks, so that a receiver can reconstruct the envelope from a subset of chunks. This introduces additional complexity and may lead to higher bandwidth usage. However, it may mitigate "coupon collector" problems, where a receiver missing a small number of chunks may wait a long time to receive them. Such an extension would be a second `ChunkingScheme`, with its parity chunks in the index space, which holds more than three times the plain scheme's largest count; it would likely compress the body first, since parity chunks may compress poorly. The code itself is left open. A Reed-Solomon code over a binary field is fast to encode and decode; beyond 256 chunks it needs GF(2^16) rather than GF(2^8). The Reed-Solomon code over the BLS12-381 scalar field, which `c-kzg` implements for blobs, admits KZG proofs that every chunk lies on one codeword. Computing them would fall on the builder's critical path, they are not post-quantum, and a payload that every node needs whole does not need them: a node that decodes can re-encode the result and check it against the root. `c-kzg` also fixes its layout, 64 cells extended to 128 per blob.
- Recovery of the parts. A node missing chunks or the signature requests the whole signed envelope by root, as today. Requests for the signature alone, or for chunks by `(payload_chunks_root, index)`, would save bandwidth for a node that misses little; they are left to a later revision.
- In future it might be considered to introduce a `bal_chunks` topic following the same broadcasting scheme for Block Access List (BAL, [EIP-7928](./eip-7928.md)) messages, which are currently part of the execution payload. This would allow BAL message propagation to start sooner than the rest of the payload.
- Which blocks open the gate. Two options. (a) Any block the node has seen, whether it passed gossip validation or was processed, as a block fetched by root is: the chunks of a fetched block then flow, which is what the chunk's `beacon_block_root` hint is kept for, but a proposer that signs two blocks for a slot can make one node forward a set for each block it processes, which is slashable. (b) Only the first block a node sees for a proposer and slot, by either path: one set per proposer and slot at each node, but a node that saw one block first forwards no chunks for the other, even if the chain takes it. In the honest case they agree. This EIP specifies (a), with a slight preference.
- Whether the descriptor checks reject. Two options. (a) IGNORE, as specified: this EIP rejects a chunk only for what the message itself gets wrong, the proof against the root it carries and the index bound. (b) REJECT: since the hint names the block, a node and the next hop check a chunk against the same descriptor, so a chunk that fails was forwarded without the check, and rejecting it would penalise the peer that forwarded it. This EIP specifies (a), with a slight preference.

## Backwards Compatibility

The `execution_payload` topic is removed and the execution bid gains a field, so this change is not backwards compatible and requires a fork.

## Security Considerations

Chunks are not individually signed; their authenticity derives from the signed block that carries the bid, via `payload_chunks_root`. Until the block is processed, the proposer's signature vouches for the root. Processing checks the builder's signature on the bid and that the builder can cover it; a self-build carries no builder signature and bids zero. The root carried in a chunk is unauthenticated on its own, but a chunk is only forwarded once the bid of a valid beacon block has committed to that root. A chunk whose proof fails against the root it carries is rejected at the first hop; a chunk under a root no block has named is held within the buffer bounds and never forwarded, so unsigned chunk spam costs each node a bounded amount of memory and no forwarding bandwidth.

`slot` and `beacon_block_root` are covered by neither the bid signature nor the inclusion proof, which is why the specification restricts their use to hints for windowing chunks and routing lookups. The consistency checks in gossip validation bound their misuse: a chunk replayed with a divergent `slot` is ignored unless that slot is current, and then finds no block for it naming its root, so it leaves the buffer unforwarded; a divergent `beacon_block_root` is ignored, not rejected, once the block containing the bid is seen: a peer may forward such a chunk honestly when the proposer has signed two blocks carrying the same bid, so a mismatch cannot be attributed to the sender. Because the chunk bytes are proof-bound, a message that differs only in these hint fields cannot alter the reconstructed envelope; because the message id covers the whole message, a copy with a rewritten hint, like a message with a garbage chunk or proof under the honest root and index, is a distinct message that neither stands in for the honest one nor occupies its id in the seen cache; and because the first-seen tuple is recorded only on acceptance, the honest copy is still accepted when it arrives.

Per-index equivocation is not possible: two distinct chunks that both verify at the same `(payload_chunks_root, index)` would imply a collision in the Merkle tree, so at most one chunk per index can propagate for a given commitment.

The `chunk.index` bound against `MAX_EXECUTION_PAYLOAD_CHUNKS` is load-bearing: `is_valid_merkle_branch` reads only the low `CHUNK_INCLUSION_PROOF_DEPTH` bits of the index, so without it the same chunk could propagate again under a larger index with the same low bits.

The descriptor's values are checked against the format's limits and the scheme's rules before any chunk is forwarded under them, and each chunk's length against the descriptor, so a bid cannot make nodes carry more than `chunk_count` messages of at most `chunk_size` bytes for its set; under the plain scheme, at most `MAX_PAYLOAD_SIZE` bytes. The two checks against the descriptor are IGNOREs, not REJECTs, like the other chunk checks that depend on a block rather than on the message alone: what a sender answers for is the proof against the root its chunk carries and the index bound of the message. A node uses the descriptor of the block named by the hint; seeing another block with the same chunks root does not make those descriptors interchangeable (see the open questions). A bid whose scheme a node does not implement is ignored, not rejected, for the same reason in another form: the node cannot tell a scheme it has not adopted yet from one that does not exist, and rejecting would let the nodes that have not upgraded penalise the peers that have.

Pre-block buffering is bounded per peer and per root, and a chunk enters it only after its inclusion proof has been checked against the root it carries. A peer can fill its own share with chunks under roots no block will name, and nothing else: its chunks cannot displace another peer's, a chunk dropped for lack of room stays open to copies from other peers, and every buffered chunk is dropped at the end of its slot. A proposer that signs two blocks for one slot, each naming a different root, causes both chunk sets to be forwarded; the equivocation is slashable, and the `beacon_block` topic forwards only the first block per proposer per slot.

Gossip validity of a chunk does not imply validity of the reconstructed envelope; full envelope validation still happens after reconstruction, as under [EIP-7732](./eip-7732.md). What this EIP changes is that the signed envelope arrives in two parts. Only the builder, or the proposer when self-building, can produce a signature message that verifies, and it verifies only for the block it names, so a third party can do nothing with it but relay it. A verified message is forwarded once per block, so each relay performs at most one signature verification per block for valid messages; invalid ones are rejected and counted against their sender, as today's envelope signatures are. A builder that signs two payloads for one block makes nodes hold different signatures, and only the nodes whose signature matches the committed chunks hold the payload; it can harm nothing but its own payload, which it could withhold outright, and the nodes without it recover the signed envelope by root. The two parts can also be delivered selectively, so that committee members hold the payload at different times; a single envelope arriving at different times has the same effect today, and a builder that wants its payload counted present sends the signature early.
